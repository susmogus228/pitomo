# Разделы и ассортимент каталога

В каталоге сохранены технические категории `food` и `accessory`. Поле `product_kind` задаёт раздел магазина и может быть `null` у старых неклассифицированных товаров.

| Значение | Раздел | category |
|---|---|---|
| food | Корма | food |
| treats | Лакомства | food |
| toys | Игрушки | accessory |
| bowls | Миски и поилки | accessory |
| litter | Наполнители | accessory |
| habitats | Домики и переноски | accessory |
| walking | Прогулка | accessory |
| care | Уход | accessory |
| aquatics | Аквариумистика | accessory |
| terrariums | Террариумы | accessory |

`GET /api/v1/products` принимает фильтр `product_kind`. Он сочетается с остальными фильтрами через AND. Несовместимое сочетание допустимых фильтров возвращает пустую страницу 200, неизвестное значение — 422. Цена и наличие проверяются у одного варианта товара; ответ сохраняет полный список вариантов для выбора в интерфейсе.

`GET /api/v1/product-kinds?pet_type=cat` возвращает десять объектов `{id, name, count}`, включая нулевые. Count считает товары для указанного `pet_type`, независимо от поисковой строки, бренда, цены и наличия. Точное число результатов комбинированного запроса находится в `ProductPage.total`. Без `pet_type` считаются все товары. Прежний `/api/v1/categories` сохранён.

Старые POST без нового поля работают: `food` получает раздел `food`, `accessory` — `null`. PATCH без `product_kind` его не меняет. Явный `null` в PATCH отклоняется, как и в остальных редактируемых полях. Несовместимые kind/category отклоняются доменом и ограничением БД. Схема API доступна в `/openapi.json`.

## Обновление демонстрационных данных

Команды выполняются в окружении проекта с настроенным `PETSHOP_DATABASE_URL`. Перед обновлением существующей базы сохранить резервную копию.

```text
python -m app.db.cli upgrade
python -m app.db.cli seed-pitomo
python -m app.db.cli refresh-demo-metadata --dry-run
python -m app.db.cli refresh-demo-metadata --apply
```

Миграция `0006_v081` добавляет nullable-колонку и заполняет `food` для существующих кормов. Для известных неизменённых демотоваров предыдущей версии она также заполняет раздел по замороженной карте SKU, проверяя бренд, группу, категорию, название, изображение, описание и единственный вариант. Другие поля не меняются. Произвольные аксессуары автоматически по названию не классифицируются.

`seed-pitomo` создаёт недостающие позиции из 48 демотоваров: восемь групп животных, по шесть товаров. В базе с предыдущими 24 демотоварами добавляются 24 новых. SKU, ID, цены, остатки, метки вариантов и metadata существующих записей не перезаписываются. Чужая запись с зарезервированным SKU и несовместимой принадлежностью вызывает ошибку; транзакция откатывается. Повторный запуск не пополняет проданные остатки.

`refresh-demo-metadata` без флагов тоже работает как dry-run. Он рассматривает только старые зарезервированные SKU 01–03, проверяет бренд, группу, категорию, единственный вариант и известные значения metadata. Пользовательские изменения пропускаются с причинами `metadata-changed` или `identity-changed`; отсутствующие записи отмечаются `missing`.

С `--apply` обновляются только название, его нормализованное значение, изображение, раздел и демонстрационное описание. Изменённые пользователем цена, метка и остаток варианта сохраняются. Привязки корзин/избранного и исторические снимки заказов не изменяются. Повторное применение сообщает `unchanged`. Команда не запускается автоматически при старте сервера.

Новые картинки ожидаются в `/media/products/v2/{asset}.webp`, перечень — `app/db/pitomo_assortment.py`. Это демонстрационные товары; состав и совместимость перед реальной продажей требуют проверки.

Откат версии приложения возможен с сохранённой дополнительной колонкой. Деструктивный downgrade схемы запрещён, чтобы не потерять классификацию и последующие изменения данных.
