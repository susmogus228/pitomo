# Petshop API v0.1.0 — первый рабочий прототип

## 1. Назначение версии

Версия **v0.1.0** — первая рабочая контрольная точка проекта «Зоомагазин».

Её задача была не построить весь интернет-магазин, а проверить три основы проекта:

1. предметную ООП-модель товаров;
2. работу FastAPI;
3. чтение демонстрационного каталога через HTTP API.

На этом этапе проект сознательно оставался простым: без SQL, авторизации, корзины, заказов и frontend.

Главный вопрос версии:

> Можно ли на основе наших классов поднять работающий API каталога и проверить основные сценарии чтения?

Ответ после завершения v0.1 — да.

---

## 2. Что реализовано в v0.1

В версии есть:

- FastAPI-приложение;
- 20 демонстрационных товаров;
- товары для кошек и собак;
- категории `food` и `accessory`;
- классы `Product`, `Food`, `Accessory`, `ProductVariant`, `Catalog`;
- несколько вариантов одного товара;
- цены в KZT;
- остатки;
- поиск по названию и SKU;
- фильтрация;
- сортировка;
- пагинация;
- Swagger/OpenAPI;
- health-check;
- автоматические тесты.

Данные находятся только в оперативной памяти и создаются заново при каждом запуске приложения.

## 4. Предметная модель

### Product

Базовый класс товара.

Основные данные:

```text
id
name
pet_type
brand
variants
```

### Food

Наследуется от `Product` и добавляет:

```text
composition
```

Категория:

```text
food
```

### Accessory

Наследуется от `Product` и добавляет:

```text
material
```

Категория:

```text
accessory
```

### ProductVariant

Представляет конкретный покупаемый вариант товара.

Например:

```text
Корм для кошек
├── 400 г
└── 2 кг
```

У варианта есть:

```text
id
sku
label
price
currency
stock
```

Цена и остаток инкапсулированы и изменяются через методы объекта.

### Catalog

В v0.1 класс `Catalog` выполняет роль простого in-memory хранилища товаров.

Он умеет:

```text
all()
get(product_id)
```

## 5. ООП в v0.1

### Наследование

```text
Product
├── Food
└── Accessory
```

`Food` и `Accessory` используют общую модель `Product`, но добавляют собственные свойства.

### Полиморфизм

Оба подкласса переопределяют:

```python
get_description()
```

Один и тот же вызов возвращает описание в зависимости от реального типа объекта.

### Инкапсуляция

В `ProductVariant` цена и остаток скрыты:

```text
__price
__stock
```

Для изменения используются:

```text
change_price()
set_stock()
```

`Catalog` также скрывает внутреннюю коллекцию товаров.

### Абстракция предметной области

API работает не просто со словарями, а с объектами:

```text
Product
Food
Accessory
ProductVariant
Catalog
```

Это стало фундаментом для дальнейшего развития проекта.

## 6. Демонстрационные данные

При каждом запуске `demo_catalog()` создаёт 20 товаров.

```text
1–10   food
11–20  accessory
```

Тип животного чередуется:

```text
cat
dog
```

У первых пяти кормов есть по два варианта упаковки.

Все бренды, составы, цены и названия являются тестовыми данными проекта.

## 7. API v0.1

| Метод | Endpoint | Назначение |
|---|---|---|
| GET | `/health` | Проверка состояния API |
| GET | `/api/v1/products` | Получить каталог |
| GET | `/api/v1/products/{product_id}` | Получить один товар |
| GET | `/api/v1/categories` | Получить категории |
| GET | `/api/v1/brands` | Получить бренды |
| GET | `/docs` | Swagger UI |
| GET | `/openapi.json` | OpenAPI schema |

Версия v0.1 является **read-only**: через API нельзя создавать, изменять или удалять товары.

## 8. Поиск и фильтрация

Пример:

```text
/api/v1/products?pet_type=cat&category=food&in_stock=true&max_price=5000&page_size=5
```

Поддерживаются параметры:

```text
q
pet_type
category
brand
min_price
max_price
in_stock
sort
page
page_size
```

### Поиск

`q` ищет без учёта регистра:

- по названию товара;
- по SKU вариантов.

### Фильтры

Все активные фильтры объединяются через `AND`.

Цена и наличие должны совпасть у одного и того же варианта товара.

### Сортировка

Поддерживаются:

```text
id
name
price_asc
price_desc
```

Для сортировки по цене используется минимальная цена варианта, который соответствует текущим фильтрам.

### Пагинация

Ответ списка имеет формат:

```json
{
  "items": [],
  "total": 20,
  "page": 1,
  "page_size": 20
}
```

## 9. Что v0.1 сознательно не умеет

В этой версии отсутствуют:

```text
POST /products
PATCH /products/{id}
DELETE /products/{id}
```

Также отсутствуют:

- постоянное хранение данных;
- PostgreSQL;
- SQLAlchemy;
- Alembic;
- пользователи;
- регистрация;
- авторизация;
- JWT;
- корзина;
- заказы;
- роли;
- admin API;
- frontend;
- Docker.

Это не незавершённость конкретной версии, а сознательная граница v0.1.

## 10. Ограничение архитектуры v0.1

Главный недостаток версии — слишком большая ответственность `app/main.py`.

Поток фактически выглядит так:

```text
HTTP endpoint
      ↓
поиск
фильтрация
сортировка
пагинация
      ↓
Catalog
```

То есть HTTP-слой одновременно занимается и web-задачами, и бизнес-логикой каталога.

Для небольшого прототипа это допустимо. Для корзины, заказов и SQL такая структура уже станет неудобной.

Именно это ограничение стало главной причиной перехода к v0.2.

## 12. Почему следующая версия — v0.2.0

v0.1 доказала, что базовый каталог и API работают.

Следующий этап уже меняет не только отдельную функцию, но и устройство приложения:

```text
v0.1
HTTP + Catalog

       ↓

v0.2
Router → Service → Repository → Memory
```

Поэтому следующая версия обозначена как **v0.2.0**, а не `v0.1.1`.

`0.1.1` подошла бы для небольшого исправления v0.1 без нового архитектурного этапа.

## 14. Запуск v0.1.0 с нуля

> Этот раздел относится к отдельному архиву исходников **v0.1.0**. В актуальном архиве v0.7.0 этот файл хранится как историческая документация.

Требования: Python 3.12+. PostgreSQL и Docker для v0.1 не нужны — данные находятся в памяти процесса.

### 1. Распаковать архив и перейти в папку проекта

```powershell
cd C:\Users\s.kirill\Desktop\petshop-api-v0.1
```

### 2. Создать виртуальное окружение

```powershell
python -m venv .venv
```

### 3. Установить зависимости

```powershell
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Для запуска тестов дополнительно:

```powershell
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

### 4. Запустить API

```powershell
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --no-use-colors
```

Проверка:

```text
Swagger  http://127.0.0.1:8000/docs
Products http://127.0.0.1:8000/api/v1/products
```

### 5. Запустить тесты

```powershell
.venv\Scripts\python.exe -m pytest -q
```

В v0.1 нет постоянной БД: после перезапуска процесса состояние возвращается к демонстрационным данным.
