# Petshop API v0.7.0 — Roles + Admin API

`v0.7.0` добавляет разграничение прав доступа поверх PostgreSQL/SQLAlchemy-архитектуры из `v0.6.0`.

Главная цель версии — разделить обычного покупателя и администратора магазина, не добавляя публичный способ получить повышенные права.

## Почему версия стала v0.7.0

`v0.6.0` уже имела постоянное PostgreSQL-хранилище, но любой клиент API мог изменять каталог. Это было допустимо на раннем учебном этапе, но не соответствует реальной архитектуре магазина.

В `v0.7.0` появляются:

- роли `customer` и `admin`;
- проверка прав на уровне FastAPI dependencies;
- отдельный Admin API;
- admin-only CRUD каталога;
- управление ролью и активностью пользователей;
- безопасный локальный bootstrap первого администратора;
- Alembic migration `0002_v070`.

Это функциональное расширение API и схемы БД, поэтому используется новая minor-версия `0.7.0`, а не patch `0.6.1`.

---

## Роли

### customer

Обычный зарегистрированный пользователь.

Может:

- смотреть каталог;
- работать со своим профилем;
- работать со своей корзиной;
- оформлять заказы;
- смотреть только свои заказы.

Не может:

- создавать/изменять/удалять товары;
- управлять вариантами товаров;
- видеть список пользователей;
- менять роли пользователей.

### admin

Администратор наследует все обычные возможности пользователя и дополнительно может:

- создавать товары;
- изменять товары;
- удалять товары;
- создавать/изменять/удалять варианты;
- просматривать пользователей;
- менять `customer ↔ admin`;
- деактивировать и активировать пользователей.

## Архитектура авторизации

JWT по-прежнему хранит только идентичность пользователя, а не роль.

```text
Bearer JWT
   ↓
get_current_user()
   ↓
User загружается из PostgreSQL
   ↓
require_admin()
   ↓
role == admin ?
   ├── да  → endpoint выполняется
   └── нет → 403 Forbidden
```

Это важно: если администратор меняет роль пользователя, уже выпущенный JWT не нужно перевыпускать. На следующем запросе роль снова читается из БД.

Аналогично деактивация пользователя мгновенно делает его существующие JWT недействительными, потому что `AuthService.user_from_token()` проверяет `is_active` в базе.

## Изменение доменной модели User

`User` получил поле:

```text
role = customer | admin
```

И методы:

```python
user.change_role('admin')
user.set_active(False)
user.is_admin
```

Регистрация через:

```http
POST /api/v1/auth/register
```

всегда создаёт:

```json
{
  "role": "customer"
}
```

Поле `role` нельзя передать при регистрации: Pydantic schema использует `extra='forbid'`.

Это закрывает публичное повышение привилегий.

## Изменение БД

Добавлена migration:

```text
0002_v070_roles_admin.py
```

Она добавляет в таблицу `users`:

```sql
role VARCHAR(32) NOT NULL DEFAULT 'customer'
```

и constraint:

```sql
CHECK (role IN ('customer', 'admin'))
```

Все пользователи, существовавшие до v0.7, после migration получают:

```text
role = customer
```

### История миграций

```text
0001_v060
    ↓
0002_v070
```

## Admin API

Все endpoints ниже требуют JWT пользователя с `role=admin`.

### Список пользователей

```http
GET /api/v1/admin/users
```

### Один пользователь

```http
GET /api/v1/admin/users/{user_id}
```

### Изменение доступа

```http
PATCH /api/v1/admin/users/{user_id}
```

Пример повышения роли:

```json
{
  "role": "admin"
}
```

Деактивация:

```json
{
  "is_active": false
}
```

Повторная активация:

```json
{
  "is_active": true
}
```

Можно изменить оба поля одновременно:

```json
{
  "role": "customer",
  "is_active": true
}
```

### Защита от self-lockout

Администратор не может через Admin API:

- снять собственную роль `admin`;
- деактивировать собственную учётную запись.

Такой запрос получает:

```http
409 Conflict
```

Это не мешает одному администратору изменять другого администратора.

---

## Защита каталога

В `v0.6` операции записи были публичными. В `v0.7` они требуют admin JWT.

Публичными остаются:

```http
GET /api/v1/products
GET /api/v1/products/{product_id}
GET /api/v1/categories
GET /api/v1/brands
```

Только admin:

```http
POST   /api/v1/products
PATCH  /api/v1/products/{product_id}
DELETE /api/v1/products/{product_id}

POST   /api/v1/products/{product_id}/variants
PATCH  /api/v1/products/{product_id}/variants/{variant_id}
DELETE /api/v1/products/{product_id}/variants/{variant_id}
```

Ответы:

```text
401 — JWT отсутствует/повреждён/просрочен
403 — JWT корректный, но пользователь не admin
```

# Первый администратор

Публичного endpoint вида `/make-me-admin` нет.

Первый admin создаётся локальной CLI-командой, которая работает напрямую с БД:

```powershell
.venv\Scripts\python.exe -m app.admin.bootstrap `
  --email admin@example.com `
  --password StrongAdmin123 `
  --first-name Admin
```

С фамилией:

```powershell
.venv\Scripts\python.exe -m app.admin.bootstrap `
  --email admin@example.com `
  --password StrongAdmin123 `
  --first-name Admin `
  --last-name Petshop
```

Если email ещё не существует — пользователь создаётся как `admin`.

Если пользователь уже существует — локальная команда:

- повышает его до `admin`;
- активирует;
- устанавливает переданный пароль;
- обновляет имя.

После появления первого admin остальные роли можно менять через Swagger Admin API.

# Чистая установка v0.7.0 с нуля

Этот сценарий рассчитан на новый компьютер/новую папку проекта, когда старой БД и контейнера нет.

Требования:

- Python 3.12+;
- Docker Desktop + Docker Compose;
- архив исходников `petshop-api-v0.7.0`.

При использовании Docker Desktop отдельно устанавливать PostgreSQL не нужно.

### 1. Проверить Docker

```powershell
docker --version
docker compose version
```

### 2. Перейти в проект

```powershell
cd C:\Users\s.kirill\Desktop\petshop-api-v0.7.0
```

### 3. Создать `.venv` и установить зависимости

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### 4. Создать и запустить PostgreSQL-контейнер

```powershell
docker compose up -d postgres
docker compose ps
```

Ожидаемый status PostgreSQL:

```text
Up ... (healthy)
```

### 5. Выполнить все migrations

```powershell
.venv\Scripts\python.exe -m alembic upgrade head
```

На чистой БД выполнятся обе migration:

```text
0001_v060
    ↓
0002_v070
```

### 6. Создать первого admin

```powershell
.venv\Scripts\python.exe -m app.admin.bootstrap `
  --email admin@example.com `
  --password StrongAdmin123 `
  --first-name Admin
```

### 7. Запустить API

```powershell
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --no-use-colors
```

### 8. Проверить

```text
API      http://127.0.0.1:8000/
Swagger  http://127.0.0.1:8000/docs
Health   http://127.0.0.1:8000/health
```

`/health` должен вернуть:

```json
{
  "status": "ok",
  "storage": "postgresql"
}
```

## Swagger workflow для администратора

```text
bootstrap admin в PowerShell
        ↓
POST /api/v1/auth/login
        ↓
copy access_token
        ↓
Swagger → Authorize
        ↓
Admin API / Catalog write endpoints
```

Обычная регистрация через Swagger создаёт только `customer`.

## Что сознательно не входит в v0.7

- granular permissions (`catalog.write`, `orders.manage` и т.д.);
- отдельные роли manager/operator;
- refresh tokens;
- admin order management;
- frontend admin panel;
- audit log действий администраторов.

Для текущего учебного этапа две роли дают понятную RBAC-модель без преждевременного усложнения.
