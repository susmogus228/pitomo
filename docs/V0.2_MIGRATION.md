# Документация перехода Petshop API с v0.1 на v0.2

## 1. Зачем появилась версия v0.2

Версия **v0.1.0** была сознательно сделана как минимальный прототип: показать предметную ООП-модель, поднять FastAPI, вернуть каталог из памяти и проверить поиск, фильтры, сортировку и пагинацию.

Она отвечала на вопрос: **«Работает ли базовая модель каталога и HTTP API?»**

После проверки прототипа следующий вопрос стал другим: **«Можно ли безопасно развивать этот код до корзины, заказов и SQL, не превращая `main.py` в один большой файл?»**

Именно поэтому версия поднята до **v0.2.0**. Это не исправление одной ошибки, а новый функциональный и архитектурный этап:

1. появился CRUD товаров;
2. появилась работа с вариантами товара через API;
3. появились Repository и Service слои;
4. бизнес-логика вынесена из HTTP-маршрутов;
5. предметные классы отделены от FastAPI/Pydantic;
6. сохранена обратная совместимость существующих GET endpoints v0.1.

По смыслу SemVer это **minor update**: API расширился новыми возможностями, но существующие публичные маршруты чтения не были намеренно сломаны.

---

## 2. Как выглядела v0.1

Основная структура была простой:

```text
app/
├── main.py
├── catalog.py
└── schemas.py
```

`catalog.py` содержал:

- `Product`;
- `Food`;
- `Accessory`;
- `ProductVariant`;
- `Catalog`;
- генерацию 20 демонстрационных товаров.

`main.py` одновременно выполнял несколько задач:

- создавал FastAPI;
- создавал каталог;
- объявлял HTTP endpoints;
- выполнял поиск;
- фильтровал товары;
- сортировал;
- делал пагинацию;
- формировал ошибки.

Для прототипа это было допустимо. Для следующего этапа — уже неудобно.

---

## 3. Главная архитектурная проблема v0.1

В v0.1 HTTP-слой слишком много знал о внутренностях каталога.

Условно поток выглядел так:

```text
HTTP endpoint
    ↓
сам ищет товары
сам фильтрует
сам сортирует
сам обращается к Catalog
```

Если в таком состоянии добавить SQL, корзину и заказы, `app/main.py` быстро станет связанным со всеми частями проекта.

Это усложнит:

- тестирование;
- замену памяти на PostgreSQL;
- повторное использование бизнес-логики;
- объяснение ООП-архитектуры проекта;
- поддержку новых модулей.

---

## 4. Архитектура v0.2

В v0.2 поток разделён:

```text
HTTP Request
      ↓
Router
      ↓
CatalogService
      ↓
ProductRepository
      ↓
InMemoryProductRepository
```

### Router

Файл: `app/catalog/router.py`

Отвечает только за HTTP:

- URL;
- HTTP method;
- query/body параметры;
- response model;
- status code.

Router не должен знать, как именно хранятся товары.

### Service

Файл: `app/catalog/service.py`

Содержит бизнес-сценарии:

- поиск и фильтрацию;
- создание товара;
- изменение товара;
- удаление товара;
- операции с вариантами;
- проверку уникальности SKU;
- правила `food` / `accessory`.

### Repository

Файл: `app/catalog/repository.py`

`ProductRepository` — абстрактный контракт хранилища.

```text
ProductRepository
       ↑
       │
InMemoryProductRepository   ← v0.2
       │
SQLProductRepository        ← будущая версия
```

Сегодня данные находятся в словаре Python. Позже можно реализовать SQL-репозиторий, сохранив Service и Router.

### Domain model

Файл: `app/catalog/models.py`

Содержит чистые предметные классы:

```text
Product
├── Food
└── Accessory

ProductVariant
```

В этом файле нет FastAPI, Pydantic и SQL. Это сделано специально: предметная модель не должна зависеть от способа доставки HTTP-запроса или хранения данных.

---

## 5. Что стало с классом Catalog

В v0.1 класс `Catalog` одновременно выступал коллекцией объектов и простым хранилищем.

В v0.2 его ответственность заменена на два более конкретных слоя:

```text
Catalog v0.1
   ↓
ProductRepository + CatalogService v0.2
```

Это не потеря ООП. Наоборот, теперь обязанности разделены яснее:

- Repository отвечает за доступ к объектам;
- Service отвечает за операции над каталогом;
- Product и его подклассы отвечают за собственное состояние и поведение.

---

## 6. Почему Product и ProductVariant разделены

Товар и покупаемая единица — не одно и то же.

Пример:

```text
Royal Canin Sterilised        Product
├── 400 г / RC-400            ProductVariant
├── 2 кг / RC-2000            ProductVariant
└── 4 кг / RC-4000            ProductVariant
```

Цена, остаток и SKU относятся к конкретному варианту, а название, бренд, животное и категория — к общей карточке товара.

Это важно для будущей корзины: пользователь будет добавлять в неё `variant_id`, а не абстрактный `product_id`.

---

## 7. Новый CRUD товаров

Добавлены маршруты:

```text
POST   /api/v1/products
PATCH  /api/v1/products/{product_id}
DELETE /api/v1/products/{product_id}
```

Существующие маршруты чтения сохранены:

```text
GET /api/v1/products
GET /api/v1/products/{product_id}
GET /api/v1/categories
GET /api/v1/brands
```

Это позволяет проверять новые возможности, не ломая сценарии v0.1.

---

## 8. Работа с вариантами товара

Добавлены:

```text
POST   /api/v1/products/{product_id}/variants
PATCH  /api/v1/products/{product_id}/variants/{variant_id}
DELETE /api/v1/products/{product_id}/variants/{variant_id}
```

Вариант содержит:

- `id`;
- `sku`;
- `label`;
- `price`;
- `currency = KZT`;
- `stock`.

SKU уникален для всего каталога без учёта регистра.

Например, `ABC-1` и `abc-1` считаются одним SKU.

---

## 9. Почему category нельзя менять PATCH-запросом

В этом проекте категория отражена не просто строкой, а классом:

```text
Food(Product)
Accessory(Product)
```

Если разрешить:

```json
{"category": "accessory"}
```

для существующего объекта `Food`, объект должен фактически сменить свой Python-класс и вместо `composition` начать использовать `material`.

Для v0.2 это создаёт ненужную неоднозначность. Поэтому правило простое:

> Категория задаётся при создании и не меняется через PATCH.

Если в будущем будет нужен перенос товара между категориями, это можно оформить отдельным бизнес-сценарием миграции.

---

## 10. Правила Food и Accessory

Для `food` обязательно:

```text
composition
```

Для `accessory` обязательно:

```text
material
```

Лишнее категорийное поле отклоняется. Например, `material` нельзя передавать при создании `food`.

Так API не позволяет создавать противоречивые доменные объекты.

---

## 11. Инкапсуляция и проверки

`ProductVariant` не даёт произвольно записывать цену и остаток.

Используются методы:

```text
change_price()
set_stock()
change_sku()
change_label()
```

`Product` управляет своей коллекцией вариантов через:

```text
add_variant()
remove_variant()
get_variant()
```

Также в v0.2 нельзя удалить единственный вариант товара. Иначе карточка останется без покупаемого SKU.

---

## 12. Ошибки API

### 404 Not Found

Используется, если не найден:

- товар;
- вариант товара.

### 409 Conflict

Используется при конфликте уникальности SKU.

### 422 Unprocessable Entity

Используется для:

- неверной цены;
- отрицательного остатка;
- пустых обязательных данных;
- `min_price > max_price`;
- неправильного категорийного поля;
- попытки удалить единственный вариант.

## 13. Что осталось совместимым с v0.1

Сохранены:

- 20 стартовых товаров;
- ID стартовых товаров и вариантов;
- `/health`;
- `/api/v1/products`;
- `/api/v1/products/{id}`;
- `/api/v1/categories`;
- `/api/v1/brands`;
- поиск по названию и SKU;
- фильтры;
- сортировка;
- пагинация;
- логика совместной проверки цены и наличия на одном варианте;
- строковое представление цены в response;
- KZT;
- Swagger `/docs`.

Оригинальные тесты v0.1 оставлены в проекте и запускаются вместе с новыми тестами.

---

## 14. Почему SQL всё ещё не добавлен

Цель v0.2 — проверить архитектуру и бизнес-логику до появления постоянного хранилища.

Если подключить PostgreSQL одновременно с CRUD, Repository, Service, пользователями и корзиной, станет труднее понять источник ошибок.

Поэтому пока:

```text
Repository
    ↓
Memory
```

Позже:

```text
Repository
    ↓
PostgreSQL
```

При этом внешний HTTP API не обязан меняться.

---

## 15. Что означает версия 0.2.0

Используется схема:

```text
MAJOR.MINOR.PATCH
0.2.0
```

`0` — проект всё ещё находится до стабильной версии `1.0`.

`2` — появился новый функциональный этап: CRUD + новая архитектура.

Последний `0` — это первая сборка ветки v0.2 без отдельного patch-релиза.

Пример дальнейшего изменения:

```text
0.2.1 — исправление бага без изменения основной функциональности
0.3.0 — следующий функциональный этап, например Users/Auth
1.0.0 — согласованная стабильная версия магазина/API
```

## 17. Roadmap после v0.2

После стабилизации v0.2 проект развивается постепенно, без скачка сразу от инфраструктуры к `v1.0`:

```text
v0.1  Read-only catalog                         ✅
  ↓
v0.2  Architecture + Catalog CRUD              ✅
  ↓
v0.3  Users + Authentication
  ↓
v0.4  Cart
  ↓
v0.5  Orders
  ↓
v0.6  PostgreSQL + SQLAlchemy
  ↓
v0.7  Roles + Admin API
  ↓
v0.8  Frontend integration preparation
  ↓
v0.9  Full backend/frontend integration + QA
  ↓
v1.0  Stable complete release
```

### v0.3 — Users + Authentication

Добавляется пользовательская модель и базовый контур аутентификации. На этом этапе важно отделить аккаунты от каталога и подготовить основу для персональной корзины и заказов.

### v0.4 — Cart

Появляется корзина. В неё должен попадать конкретный `variant_id`, потому что покупатель выбирает конкретный SKU товара, а не абстрактный `product_id`.

### v0.5 — Orders

Добавляется оформление заказа, позиции заказа, фиксация цены на момент покупки и изменение остатков.

### v0.6 — PostgreSQL + SQLAlchemy

In-memory repository заменяется постоянным хранилищем. К этому моменту основные бизнес-сценарии уже должны быть проверены без зависимости от SQL.

### v0.7 — Roles + Admin API

Появляются роли и административные сценарии: управление каталогом, остатками, заказами и доступом. Публичный API и административный API начинают чётко различаться по ответственности.

### v0.8 — Подготовка интеграции frontend

API приводится к форме, удобной для реального интерфейса: CORS, уточнение контрактов, обработка состояний frontend, стабилизация response-моделей и устранение неудобных для клиента мест.

### v0.9 — Полная интеграция backend/frontend + QA

Frontend и backend работают вместе как единое приложение. На этом этапе основная цель — не добавлять фундаментальные модули, а пройти сквозные сценарии, интеграционные тесты и исправление ошибок.

### v1.0 — Стабильная законченная версия

`v1.0` — первая версия, которую можно считать цельным результатом проекта. К ней основные возможности уже реализованы и интегрированы, а публичные контракты API стабилизированы.

Ключевая идея roadmap: **каждая версия `0.x` отвечает за отдельный крупный этап, а `v1.0` фиксирует завершение и стабилизацию всей первой версии магазина.**

## 18. Запуск v0.2.0 с нуля

> Инструкция относится к отдельному архиву **v0.2.0**. В актуальном v0.7.0 этот документ является историей версии.

Требования: Python 3.12+. Docker/PostgreSQL не нужны.

```powershell
cd C:\Users\s.kirill\Desktop\petshop-api-v0.2.0
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --no-use-colors
```

Swagger:

```text
http://127.0.0.1:8000/docs
```

Для тестов:

```powershell
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe -m pytest -q
```

## 19. Обновление v0.1.0 → v0.2.0

В этой версии БД ещё нет, поэтому миграция данных не требуется.

1. Распаковать v0.2.0 в отдельную папку.
2. Создать новое `.venv` либо переустановить зависимости в существующем окружении.
3. Выполнить `pip install -r requirements.txt`.
4. Запустить тесты.
5. Запустить Uvicorn.

Данные v0.1 в памяти процесса не переносятся — v0.2 стартует со своим seed-каталогом.
