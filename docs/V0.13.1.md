# Питомо 0.13.1: исправления аудита

Обновление сохраняет текущий стек и оформление магазина. Схема БД остаётся
`0011_v013`: новая миграция для этих исправлений не нужна.

## Изменения

| Аудит | Изменение |
|---|---|
| F01 | При частичной ошибке фото текст отзыва сохраняется; предупреждение остаётся, повтор отправляет только неудачные файлы. |
| F02 | Черновик оформления хранится в sessionStorage до двух часов, привязан к пользователю, восстанавливается после reload и очищается после заказа/выхода. |
| F03 | Ошибки регистрации и оформления связаны с полями через ARIA; фокус переходит к первой ошибке. |
| F04 | Во время сохранения профиля поля блокируются. После следующего изменения старое сообщение об успехе снимается. |
| F05 | Черновики товаров и вариантов сохраняются раздельно по пользователю и товару до 24 часов; есть восстановление и сброс. |
| F06 | Список пользователей получает total, страница хранится в URL; возврат доступен и с пустой страницы. Старый API списка сохранён. |
| F07 | Редактор отзыва/ответа получает фокус; сохранение и отмена возвращают его к действию. |
| F08 | Поиск учитывает название, SKU, бренд, восемь групп питомцев и товарные разделы, включая русские словоформы. |
| F09 | Главная, вход и регистрация используют WebP и подходящие размеры. PNG-оригиналы сохранены. |
| F10 | Показатели и рабочие очереди расположены перед экспортом. Скачивание доступно одной кнопкой, дополнительные параметры свёрнуты. |
| F11 | Добавлены очереди и фильтры этапа, поломки, получения и времени без обновления. Условия сохраняются в URL. |
| F12 | Экспорт содержит этап, поломку, версию, время обновления и DeliveryEvents. Фильтры совпадают с экраном. |
| F13 | Счётчики открывают соответствующие очереди; малые остатки имеют настраиваемый порог. |
| F14 | Точку карты можно выбрать с клавиатуры: стрелки и кнопка выбора центра. Добавлена инструкция. |
| F15 | Ввод цены применяется после паузы 350 мс; прежние карточки остаются во время загрузки с подписью обновления. |
| F16 | Отзывы и ответы объясняют минимальную длину и показывают счётчик символов. |
| F17 | Недоступное фото товара заменяется заглушкой без повторяющихся запросов. |
| F18 | Статические изображения получают версию содержимого в URL; nginx требует повторной проверки медиа. |
| F19 | Сортировка по ID называется «По умолчанию». |
| F20 | Заголовок вкладки содержит название товара или номер заказа. |

Дополнительно рейтинг доступен возле названия товара, ФИО согласия подставляется
из регистрационных полей и остаётся редактируемым. Приватные ресурсы учитывают ID
пользователя: снимок предыдущего аккаунта скрывается до загрузки новых данных.

## Административные API

- `GET /api/v1/admin/users/page?limit=50&offset=0` возвращает
  `{items,total,limit,offset}`. Прежний `/admin/users` возвращает список.
- `GET /api/v1/admin/products?stock_max=5&page=1&page_size=50&q=кошки`
  выбирает товары хотя бы с одним вариантом, остаток которого не больше порога.
  Возвращаются все варианты выбранного товара. Маршрут требует роль admin.
- `/admin/orders` и `/admin/exports/{dataset}` принимают одинаковые параметры
  `queue`, `delivery_stage`, `delivery_incident`, `received`, `stale_hours`.
- Экспорт каталога принимает `stock_max` и тот же поиск, что административный список.

| Очередь | Условие |
|---|---|
| active | Активные, ещё не полученные заказы, включая самовывоз и ожидающие оплату. |
| warehouse | Доставка на складе, без поломки, оплата готова или выбрана оплата при получении. |
| in_transit | То же, этап «В пути». |
| incidents | Любая активная доставка с поломкой, в том числе до оплаты. |
| awaiting_receipt | Доставка рядом с покупателем, без поломки, оплата готова. |
| received | Полученные и не отменённые заказы. |

Дополнительные фильтры сочетаются через AND. `stale_hours` применяется к активным
доставкам и проверяет последнее обновление, а при его отсутствии — создание заказа.
Это очередь проверки задержек, а не обещание времени прибытия.

`Orders`, `OrderItems` и `DeliveryEvents` используют один снимок SQL-запроса.
Произвольный JSON истории не выгружается. Заметки и текст проблемы появляются
только при `include_contacts=true`; по умолчанию контакты исключены. Пустой лист
DeliveryEvents опускается, что указано в Metadata. CSV с несколькими таблицами
скачивается ZIP-архивом.

## Обновление существующей установки

1. Сохраните резервную копию БД и тома фотографий по `OPERATIONS.md`.
2. Обновите файлы проекта из архива, сохранив исходный `.env` и
   `.petshop-project-name`. Не копируйте `.env.example` поверх рабочего `.env`.
3. Запустите `START.bat`: существующие зависимости и слои сборки используются повторно.
4. Откройте магазин и `/ready`; проверьте вход, корзину, оформление и admin.

В примере `.env` и Compose согласованы теги `petshop-api:0.13.1` и
`pitomo-web:0.13.1`. Для ручной сборки укажите эти теги и в рабочей конфигурации.
`START.bat` собирает текущие исходники; старые образы остаются доступными для отката.

## Медиа и ограничения

Для обновления одобренных PNG-мастеров используйте
`python scripts/optimize_store_media.py`, затем пересоберите frontend. Скрипт
создаёт WebP, размеры, `frontend/src/mediaVersions.json` и отчёт
`verification/audit-media-optimization.json`. При отдельной замене статического
медиа также обновите manifest этим скриптом. Пользовательские загрузки получают
собственные имена и не включаются в этот manifest.

Черновики не синхронизируются между устройствами. Фото до отправки хранятся в
памяти вкладки; после полного обновления страницы их нужно выбрать заново.
Если ответ потерян после фактического сохранения фото сервером, клиент не может
надёжно отличить этот случай от неудачной загрузки. Серверная идемпотентность
фотозагрузок остаётся отдельным улучшением.

Фактические результаты проверок и снимки находятся в `verification/` и итоговом
пакете проверки. Гайд функций и запуска: [NEXT_STEPS.md](NEXT_STEPS.md).
