# Petshop API v0.4.0 — Cart

## Зачем появилась версия 0.4.0

Версия `0.3.0` добавила пользователей и JWT-аутентификацию. После этого у приложения появилась устойчивая идентичность пользователя, а значит следующий логичный шаг — персональная корзина.

`v0.4.0` добавляет новый доменный модуль `cart` и связывает его с двумя уже существующими частями проекта:

```text
Current User ────> Cart
                    │
                    └── variant_id ────> Catalog
```

Это **minor-версия**, потому что API получает новый функциональный модуль, новые публичные endpoints, новые доменные сущности и новую бизнес-логику. Поведение каталога и авторизации предыдущих версий сохраняется.

---

## Главная цель версии

До `v0.4` приложение уже умело:

1. показывать каталог;
2. создавать и изменять товары;
3. регистрировать пользователя;
4. выдавать JWT;
5. определять текущего пользователя.

Но пользователь ещё не мог собирать будущий заказ.

Теперь появляется промежуточная сущность:

```text
User
  ↓
Cart
  ↓
CartItem
  ↓
ProductVariant
```

Корзина станет основой для `v0.5 Orders`.

---

## Новые доменные сущности

### CartItem

```text
CartItem
├── variant_id
└── quantity
```

`CartItem` не хранит полную копию товара. Он содержит только ссылку на конкретный продаваемый вариант и количество.

Это важно, потому что покупать нужно не абстрактный `Product`, а конкретный SKU:

```text
Royal Canin Sterilised
├── 400 г  ← variant_id
├── 2 кг
└── 4 кг
```

### Cart

```text
Cart
├── user_id
└── items[]
```

Один пользователь имеет одну корзину.

Внутри `Cart` позиции инкапсулированы. Изменение состояния происходит через методы:

```text
add_item()
set_quantity()
remove_item()
clear()
```

Это продолжает ООП-подход проекта: HTTP-роут не манипулирует внутренним словарём корзины напрямую.

## Новая архитектура

```text
                         FastAPI
                            │
          ┌─────────────────┼──────────────────┐
          │                 │                  │
   Catalog Router      Auth/User Router    Cart Router
          │                 │                  │
   CatalogService      Auth/UserService    CartService
          │                 │             ┌────┴─────┐
 ProductRepository     UserRepository      │          │
          │                 │         CartRepository │
          │                 │              │         │
          └────────────────────────────────┘         │
                    shared catalog lookup <──────────┘
```

Практически `CartService` зависит от двух абстракций:

```text
CartRepository
ProductRepository
```

Первый отвечает за состояние корзины, второй — за актуальную информацию о варианте товара.

## CartRepository

Контракт:

```text
CartRepository
      ↑
      │
InMemoryCartRepository
```

В `v0.4` данные находятся в памяти процесса.

Repository хранит одну корзину на `user_id`.

Позже в `v0.6` можно будет добавить SQL-реализацию без изменения HTTP-роутов корзины.

---

## CartService

`CartService` содержит бизнес-логику:

- создание пустой корзины при первом обращении;
- добавление товара;
- увеличение количества существующей позиции;
- изменение количества;
- удаление позиции;
- очистку корзины;
- проверку текущего остатка;
- получение актуальной цены;
- вычисление `line_total`;
- вычисление `subtotal`;
- вычисление `can_checkout`;
- удаление устаревшей ссылки, если вариант был удалён из каталога.

Router при этом остаётся тонким HTTP-слоем.

---

## API v0.4.0

Все endpoints корзины требуют Bearer JWT.

| Метод | URL | Назначение |
|---|---|---|
| GET | `/api/v1/cart` | Получить корзину текущего пользователя |
| POST | `/api/v1/cart/items` | Добавить количество конкретного варианта |
| PATCH | `/api/v1/cart/items/{variant_id}` | Установить точное количество |
| DELETE | `/api/v1/cart/items/{variant_id}` | Удалить позицию |
| DELETE | `/api/v1/cart` | Очистить корзину |

Каталог, регистрация, login и `/users/me` из предыдущих версий сохранены.

---

## Почему корзина работает с variant_id

`Product` — это карточка товара.

`ProductVariant` — конкретная единица продажи с собственными:

```text
SKU
ценой
остатком
размером / весом
```

Поэтому запрос выглядит так:

```json
{
  "variant_id": 20,
  "quantity": 2
}
```

А не так:

```json
{
  "product_id": 2,
  "quantity": 2
}
```

Иначе невозможно однозначно определить, какой именно вес или размер покупает пользователь.

---

## Добавление товара

```http
POST /api/v1/cart/items
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "variant_id": 20,
  "quantity": 2
}
```

Если позиции ещё нет, она создаётся.

Если тот же `variant_id` уже есть в корзине, количество увеличивается:

```text
было: 2
POST quantity=1
стало: 3
```

Перед изменением проверяется общий итоговый объём относительно остатка.

---

## PATCH количества

```http
PATCH /api/v1/cart/items/20
```

```json
{
  "quantity": 4
}
```

В отличие от `POST`, PATCH не прибавляет число, а устанавливает его точно:

```text
было: 2
PATCH quantity=4
стало: 4
```

Количество `0` не используется для удаления. Для этого есть отдельный `DELETE`.

---

## Актуальная цена вместо копии цены

В корзине хранится:

```text
variant_id + quantity
```

Цена не копируется внутрь `CartItem`.

При чтении корзины выполняется актуальный lookup:

```text
CartItem.variant_id
        ↓
ProductRepository.find_variant()
        ↓
текущая цена + текущий остаток
```

Поэтому если цена была изменена в каталоге после добавления в корзину, следующий `GET /api/v1/cart` покажет новую цену.

Это сознательное решение. Фиксация цены должна происходить уже на этапе создания заказа, а не при простом добавлении в корзину.

---

## Проверка остатка

При добавлении и PATCH действует правило:

```text
quantity <= current stock
```

Если пользователь пытается положить больше:

```http
409 Conflict
```

Пример:

```json
{
  "detail": "Недостаточно товара на складе: доступно 5, запрошено 6"
}
```

---

## Что происходит, если остаток изменился позже

Возможна ситуация:

```text
1. пользователь положил 3 шт.
2. на складе было 5
3. каталог изменили
4. на складе осталось 1
```

Корзина не удаляет позицию автоматически.

Ответ покажет:

```json
{
  "quantity": 3,
  "available_stock": 1,
  "is_available": false
}
```

А вся корзина:

```json
{
  "can_checkout": false
}
```

Это важная подготовка к `v0.5`: при создании заказа остаток должен проверяться повторно.

---

## Расчёт стоимости

Для каждой строки:

```text
line_total = current unit_price × quantity
```

Для корзины:

```text
subtotal = сумма всех line_total
```

Деньги по-прежнему считаются через `Decimal`, а не через `float`.

Ответ передаёт денежные значения строками:

```json
{
  "unit_price": "1400.00",
  "line_total": "2800.00",
  "subtotal": "2800.00",
  "currency": "KZT"
}
```

---

## can_checkout

Поле `can_checkout` в `v0.4` является подготовительным.

Оно равно `true`, когда:

- корзина не пустая;
- все позиции существуют;
- по каждой позиции текущего остатка достаточно.

Пустая корзина:

```json
{
  "can_checkout": false
}
```

Фактического checkout пока нет. Создание заказа появится в `v0.5`.

---

## Удалённый вариант товара

Поскольку CRUD каталога пока доступен, вариант товара может быть удалён уже после добавления в корзину.

В таком случае `GET /api/v1/cart` автоматически удаляет устаревшую ссылку из корзины вместо того, чтобы делать всю корзину нечитаемой.

Это временное поведение до появления ролей/Admin API и постоянной БД.

---

## Изоляция пользователей

Корзина всегда определяется через JWT:

```text
Bearer token
     ↓
CurrentUser
     ↓
user_id
     ↓
CartRepository
```

Пользователь не передаёт `user_id` в URL или JSON.

То есть API не выглядит так:

```text
/api/v1/users/15/cart
```

Для текущего клиента используется:

```text
/api/v1/cart
```

Это исключает простую подмену чужого ID на уровне HTTP-запроса.

---

## HTTP-ошибки

### 401 Unauthorized

Нет Bearer-токена, токен повреждён или просрочен.

### 404 Not Found

- `variant_id` не существует в каталоге;
- PATCH/DELETE запрашивает позицию, которой нет в корзине.

### 409 Conflict

Количество превышает текущий остаток.

### 422 Unprocessable Entity

Например:

```json
{
  "variant_id": 20,
  "quantity": 0
}
```

или передано неизвестное поле.

---

## Почему пока нет резервирования товара

Добавление в корзину **не уменьшает stock**.

Иначе простой пользователь мог бы заблокировать остаток, просто положив товар в корзину и ничего не купив.

На текущем этапе:

```text
Cart → проверяет остаток
Order → будет подтверждать и списывать остаток
```

Логику фактического списания и защиты от повторного оформления добавим в `v0.5`.

---

## Почему всё ещё нет SQL

Цель текущего этапа — закончить бизнес-модель корзины до подключения инфраструктуры БД.

Сейчас:

```text
CartService
   ↓
CartRepository
   ↓
InMemoryCartRepository
```

В `v0.6`:

```text
CartService
   ↓
CartRepository
   ↓
SQLCartRepository
```

Если контракт Repository спроектирован правильно, Router и основная логика CartService не должны переписываться с нуля.

## Переход к v0.5

Следующая версия будет строиться поверх корзины:

```text
Authenticated User
       ↓
      Cart
       ↓
  stock validation
       ↓
     Order
       ↓
   OrderItems
       ↓
 stock decrease
```

Ключевой момент `v0.5`: заказ должен сохранить снимок цены и товара на момент покупки, потому что после оформления будущие изменения каталога не должны менять уже созданный заказ.

1. Использовать код v0.4.0.

4. Зарегистрировать пользователя заново при необходимости — хранилище всё ещё in-memory.
5. Проверить endpoints `/api/v1/cart`.
