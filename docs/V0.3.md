# Petshop API v0.3.0 — Users + Authentication

## Зачем появилась версия 0.3.0

Версия `0.2.1` завершила первый крупный блок проекта: каталог товаров получил CRUD, слои `Router → Service → Repository` и in-memory хранилище. Но у API ещё не было понятия пользователя: любой запрос был анонимным, а будущую корзину было не к кому привязать.

`v0.3.0` добавляет второй доменный модуль — пользователей — и полноценный базовый сценарий аутентификации:

1. пользователь регистрируется;
2. пароль превращается в безопасный хэш и не хранится открытым текстом;
3. пользователь входит по email и паролю;
4. сервер выдаёт JWT access token;
5. Bearer-токен открывает защищённый endpoint `/api/v1/users/me`;
6. пользователь может изменить свой профиль.

Это **minor-версия**, а не patch, потому что API получает новый функциональный модуль и новые публичные endpoints. Каталог v0.2.1 при этом сохраняется.

---

## Что добавлено

### Пользователи

Новая предметная сущность:

```text
User
├── id
├── email
├── password_hash
├── first_name
├── last_name
└── is_active
```

`User` находится в `app/users/models.py` и не зависит от FastAPI, Pydantic или базы данных.

### UserRepository

Добавлен контракт хранилища:

```text
UserRepository
       ↑
       │
InMemoryUserRepository
```

Сейчас пользователи живут только в памяти процесса. В `v0.6` вместо этой реализации можно будет подключить SQL-репозиторий, сохранив сервисы и HTTP API.

### UserService

`UserService` отвечает за работу с профилем:

- получение пользователя;
- изменение email;
- изменение имени и фамилии;
- проверку уникальности нового email.

### AuthService

`AuthService` отвечает за сценарии аутентификации:

- регистрация;
- проверка email на уникальность;
- хэширование пароля;
- проверка пароля;
- login;
- создание JWT;
- проверка JWT;
- получение пользователя из токена.

## Новая архитектура

```text
                       FastAPI
                          │
              ┌───────────┴───────────┐
              │                       │
         Catalog Router          Auth / User Router
              │                       │
       CatalogService       AuthService / UserService
              │                       │
      ProductRepository            UserRepository
              │                       │
 InMemoryProductRepository  InMemoryUserRepository
```

Общие функции безопасности и конфигурации вынесены отдельно:

```text
app/core/config.py
app/core/security.py
```

Так авторизация не смешивается ни с каталогом, ни с HTTP-слоем.

## API v0.3.0

Новые endpoints:

| Метод | URL | Авторизация | Назначение |
|---|---|---|---|
| POST | `/api/v1/auth/register` | Нет | Регистрация |
| POST | `/api/v1/auth/login` | Нет | Получение JWT |
| GET | `/api/v1/users/me` | Bearer JWT | Текущий профиль |
| PATCH | `/api/v1/users/me` | Bearer JWT | Изменение профиля |

Все endpoints каталога v0.2.1 сохранены.

---

## Регистрация

Запрос:

```http
POST /api/v1/auth/register
Content-Type: application/json
```

```json
{
  "email": "user@example.com",
  "password": "StrongPass123",
  "first_name": "Kirill",
  "last_name": "Ivanov"
}
```

Ответ `201 Created`:

```json
{
  "id": 1,
  "email": "user@example.com",
  "first_name": "Kirill",
  "last_name": "Ivanov",
  "is_active": true
}
```

Пароль и его хэш никогда не входят в HTTP-ответ пользователя.

Email нормализуется в нижний регистр. Повторная регистрация того же email, в том числе с другим регистром букв, возвращает `409 Conflict`.

---

## Хранение пароля

Открытый пароль не сохраняется. Используется:

```text
PBKDF2-HMAC-SHA256
+ случайная соль
+ 310 000 итераций
```

В памяти хранится строка вида:

```text
pbkdf2_sha256$310000$<salt>$<hash>
```

Реальный пароль из запроса после регистрации больше не нужен.

---

## Login

Запрос:

```http
POST /api/v1/auth/login
Content-Type: application/json
```

```json
{
  "email": "user@example.com",
  "password": "StrongPass123"
}
```

Ответ:

```json
{
  "access_token": "<JWT>",
  "token_type": "bearer",
  "expires_in": 1800
}
```

По умолчанию access token действует **30 минут**.

При неверном email или пароле API намеренно возвращает один и тот же ответ `401`, не раскрывая, существует ли конкретный email.

---

## JWT

В v0.3 используется JWT с алгоритмом `HS256`.

Payload содержит:

```text
sub — ID пользователя
iat — время выпуска
exp — время окончания действия
```

Подпись проверяется при каждом защищённом запросе. Подменённый или просроченный токен возвращает `401 Unauthorized`.

### Секрет подписи

Для локальной учебной разработки существует значение по умолчанию. Его можно заменить переменной окружения:

PowerShell:

```powershell
$env:PETSHOP_JWT_SECRET = "change-this-secret"
```

Также можно изменить время жизни токена:

```powershell
$env:PETSHOP_ACCESS_TOKEN_MINUTES = "60"
```

После изменения переменных сервер нужно перезапустить.

---

## Защищённый запрос

После login токен передаётся так:

```http
Authorization: Bearer <access_token>
```

Пример:

```http
GET /api/v1/users/me
Authorization: Bearer eyJ...
```

Без Bearer-токена endpoint возвращает `401`.

Swagger UI автоматически показывает HTTP Bearer authentication для защищённых endpoints.

---

## Изменение профиля

```http
PATCH /api/v1/users/me
Authorization: Bearer <access_token>
```

Можно изменить:

```json
{
  "email": "new@example.com",
  "first_name": "New Name",
  "last_name": "New Last"
}
```

`email` должен оставаться уникальным. `last_name` можно очистить, передав `null`. `email` и `first_name` в `null` переводить нельзя.

Пароль через этот endpoint не изменяется. Отдельный сценарий смены/восстановления пароля пока не входит в v0.3.

---

## Почему пока нет ролей

В v0.3 существует обычный пользователь. Роли вроде `admin` сознательно не добавлены.

Они запланированы на `v0.7`, когда уже будут каталог, пользователи, корзина, заказы и SQL-хранилище. Это не смешивает базовую аутентификацию с будущей системой прав доступа.

---

## Почему всё ещё нет SQL

Это намеренное решение.

Сейчас можно проверить архитектуру и бизнес-логику пользователей без дополнительной сложности базы данных:

```text
Router
  ↓
Service
  ↓
UserRepository
  ↓
InMemoryUserRepository
```

Позже нижний слой будет заменён:

```text
UserRepository
  ↑
SQLUserRepository
```

Благодаря этому текущие endpoints и основная логика не должны быть переписаны с нуля.

---

## Ограничение in-memory версии

После перезапуска Uvicorn:

- все зарегистрированные пользователи исчезают;
- старые JWT больше не соответствуют пользователям нового процесса;
- каталог снова загружается из seed-данных.

Для v0.3 это ожидаемое поведение.

## Запуск v0.3.0 с нуля

> Инструкция относится к отдельному архиву **v0.3.0**.

Требования: Python 3.12+. PostgreSQL/Docker не нужны; пользователи и каталог хранятся in-memory.

```powershell
cd C:\Users\s.kirill\Desktop\petshop-api-v0.3.0
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --no-use-colors
```

Swagger:

```text
http://127.0.0.1:8000/docs
```

Для полного smoke-flow в Swagger: `register → login → Authorize → GET /api/v1/users/me`.

## Обновление v0.2.1 → v0.3.0

1. Распаковать v0.3.0 в отдельную папку.
2. Установить зависимости текущей версии.
3. Запустить API.
4. Зарегистрировать пользователя заново: постоянной БД ещё нет, поэтому пользователи предыдущего процесса не переносятся.
