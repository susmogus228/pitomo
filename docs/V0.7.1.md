# Изменения в Petshop API 0.7.1

Релиз исправляет подтверждённые ошибки аудита 0.7.0. API сохраняет основные
маршруты и роли. Для первого запуска используйте [README](../README.md),
для эксплуатации и восстановления базы [OPERATIONS](OPERATIONS.md).

## Исправления по аудиту

| Код | Проблема 0.7.0 | Исправление 0.7.1 | Проверка |
|---|---|---|---|
| F01 | Commit выполнялся после успешного HTTP-ответа | Завершение DB dependency со scope=function до отправки ответа; rollback при ошибке | Известный конфликт commit возвращает 409, неожиданная ошибка 500 |
| F02 | Runtime принимал статический JWT secret | Проверка конфигурации при startup и обработке запросов, минимум 32 байта, запрет шаблонных значений | Запуск без secret завершается ошибкой |
| F03 | Сохранение профиля могло восстановить старые права и пароль | UPDATE только перечисленных полей; CAS при обновлении hash | Пересекающиеся profile/admin изменения, CAS password test |
| F04 | Сохранение товара перезаписывало остатки и соседние варианты | Отдельные UPDATE метаданных и варианта | Конкурентные stock/metadata tests |
| F05 | Checkout использовал устаревший объект соседнего SKU | Чтение свежего варианта под FOR UPDATE с populate_existing | PostgreSQL sibling interleaving test |
| F06 | Локальный lock не защищал от двух checkout | Блокировка строки владельца корзины, затем SKU по ID; идемпотентный ключ заказа | Два параллельных checkout и покупка последней единицы |
| F07 | Замена корзины теряла конкурентные изменения | Блокировка владельца до чтения и изменения корзины, в том числе при первом создании | Параллельное создание и добавление товаров |
| F08 | Каталог загружался полностью для пагинации в Python | Фильтры, сортировка, count, limit и offset в SQL | Запрос страницы с контролем SQL-запросов |
| F09 | Для каждой строки корзины выполнялся отдельный запрос | Пакетная загрузка вариантов и товаров | Проверка количества запросов |
| F10 | История заказов и список пользователей не имели лимита | limit/offset, default 50, max 100; стабильная сортировка | API/repository pagination tests |
| F11 | PostgreSQL не проверялся, SQLite игнорировал FK | Отдельные PostgreSQL integration/concurrency tests; SQLite foreign_keys=ON | Реальный PostgreSQL 16 и FK constraints tests |
| F12 | OpenAPI объявлял только строковую ошибку | ErrorResponse описывает строку и список ValidationIssue | OpenAPI и HTTP422 tests |
| F13 | SELECT1 не подтверждал готовность схемы | /health для процесса, /ready для БД, таблиц, колонок и migration head | Пустая/повреждённая схема даёт 503 |
| F14 | Ошибки валидации возвращали входные значения | Удалены input/ctx; generic message для пользовательского ValueError | Проверка отсутствия пароля в response/logs |
| F15 | API пропускал значения вне PostgreSQL int4 | Ограничения DTO, домена и CHECK: ID/stock ≤2147483647, quantity ≤10000; предел цены | Границы HTTP/домена/БД |
| F16 | Гонка уникальности email/SKU завершалась необработанной ошибкой | Распознавание unique constraints и ответ 409; rollback всей транзакции | Конкурентные PostgreSQL insert tests |
| F17 | SQLite повторно выдавал удалённый ID | Постоянный счётчик ID с учётом истории и корзин при миграции | Удаление/создание не подменяет вариант в корзине |
| F18 | lower и casefold давали разные правила SKU | Python casefold в нормализованной колонке, UNIQUE в БД, backfill миграцией | Unicode/casefold конфликты и конкурентные записи |

## Безопасность и эксплуатация

- PyJWT проверяет HS256, обязательные sub/iat/exp, типы claims и канонический Base64URL.
- PBKDF2 использует 600000 итераций. Проверка старых хешей сохраняется; после успешного входа API обновляет hash через CAS. Пароль больше не обрезается по краям.
- Лимиты login/register хранятся в БД и действуют между процессами. Ключи содержат HMAC email/IP; счётчики не откатываются вместе с неуспешным запросом. При смене JWT secret набор ключей меняется.
- Bootstrap administrator читает пароль интерактивно или из stdin. В аргументах процесса пароль не передаётся.
- Production по умолчанию скрывает Swagger/OpenAPI. CORS принимает явные origins. Swagger не сохраняет токен.
- JSON audit events содержат request ID, шаблон маршрута, статус, ID пользователя и длительность. /metrics требует admin и возвращает счётчики текущего процесса.
- Docker запускает API без root и без reload; PostgreSQL доступен внутри Compose, dev override публикует БД только на loopback.
- Runtime/dev lock-файлы фиксируют версии и хеши зависимостей. CI запускает линтер, тесты, dependency audit и Compose smoke.
- Backup/restore скрипт использует pg_dump/pg_restore, проверяет отдельную пустую цель и не передаёт пароль аргументом процесса.
- Demo seed отделён от новой установки. Старые миграции сохраняют историческое поведение и пользовательские данные.
- OrderItem стал неизменяемым snapshot. Время заказа сериализуется в UTC при checkout, чтении и повторе по Idempotency-Key.

## Совместимость и ограничения

Списки пользователей и заказов сохранили JSON-массив, но теперь возвращают
не более limit записей. Для следующих страниц увеличивайте offset.
`Idempotency-Key` необязателен; его область уникальности ограничена пользователем.
Новый ключ означает новый заказ. Повтор старого ключа не очищает новую корзину.

Migration 0003 выполняет Unicode backfill при подключённой БД. Перед изменением
DDL она проверяет новые ограничения и конфликты SKU. Некорректные старые данные
нужно исправить осознанно до повторного запуска. Автоматический downgrade 0003
запрещён, поскольку он удалил бы данные идемпотентности и защиту ID; используйте
восстановление проверенного backup.

SQLite не заменяет PostgreSQL для конкурентного production. In-memory repositories
остались для последовательных доменных примеров. Тесты PostgreSQL без отдельного
URL отмечаются skip; CI задаёт одноразовую базу.

Платежи, доставка, возвраты, refresh tokens и восстановление пароля остаются
за пределами версии. Настройка production HTTPS, внешнего мониторинга, хранения
backup и удалённого CI требует инфраструктуры владельца проекта.
