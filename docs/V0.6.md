# Petshop API v0.6.0 — PostgreSQL + SQLAlchemy + Alembic

## 1. Зачем появилась v0.6

До `v0.5.0` проект уже имел полноценную бизнес-цепочку:

```text
Catalog → Users/Auth → Cart → Orders
```

Но все repository implementations хранили данные внутри Python-процесса. После перезапуска сервера исчезали пользователи, корзины, заказы, изменения каталога и списанные остатки.

`v0.6.0` решает именно эту архитектурную проблему: **данные становятся постоянными**.

Это minor-версия, а не patch, потому что меняется фундаментальный слой приложения — persistence.

## 3. Почему SQLAlchemy не встроен прямо в domain classes

Проект остаётся ООП-проектом, а не просто набором ORM-моделей.

Domain classes:

```text
Product
Food(Product)
Accessory(Product)
ProductVariant
User
Cart
CartItem
Order
OrderItem
```

по-прежнему находятся в своих `models.py` и ничего не знают про:

- FastAPI;
- SQLAlchemy;
- PostgreSQL;
- HTTP.

Отдельно появились ORM-классы:

```text
UserORM
ProductORM
ProductVariantORM
CartORM
CartItemORM
OrderORM
OrderItemORM
```

Между ними используется mapping layer:

```text
domain ← app/db/mappers.py → ORM
```

Это позволяет сохранить separation of concerns.

In-memory implementations оставлены, чтобы:

1. сохранить демонстрацию полиморфизма;
2. не связывать domain model с БД;
3. иметь простой вариант для отдельных unit/OOP примеров.

## 6. Одна Session на HTTP request

В `v0.5` каждый repository работал непосредственно с объектами в памяти.

В `v0.6` FastAPI dependency создаёт SQLAlchemy `Session`:

```text
request
  ↓
Session open
  ↓
Auth dependency
  ↓
Service
  ↓
Repositories
  ↓
route success
  ↓
COMMIT
```

При exception:

```text
exception
   ↓
ROLLBACK
   ↓
Session close
```

Auth и основной service одного запроса получают одну и ту же cached dependency Session.

Это важно, потому что действия внутри одного API-запроса становятся одной транзакцией.

## 7. Checkout теперь использует настоящую DB transaction

В `v0.5` transaction-like поведение имитировалось вручную:

```text
remember old state
→ change objects
→ error?
→ restore old state
```

В `v0.6` база сама обеспечивает atomicity.

Checkout:

```text
1. получить Cart
2. заблокировать нужные variant rows
3. проверить весь stock
4. создать OrderItem snapshots
5. уменьшить stock
6. INSERT Order
7. INSERT OrderItems
8. очистить Cart
9. COMMIT
```

При ошибке:

```text
ROLLBACK
```

Ни заказ, ни частичное списание, ни очистка корзины не должны сохраниться.

## 8. FOR UPDATE

Одной транзакции недостаточно для конкурентного checkout.

Пример проблемы без row lock:

```text
stock = 1

Request A reads 1
Request B reads 1
A buys 1
B buys 1
```

Оба запроса могли бы считать товар доступным.

Поэтому `SQLAlchemyProductRepository.find_variant(..., for_update=True)` использует:

```sql
SELECT ... FOR UPDATE
```

PostgreSQL блокирует строку варианта до завершения transaction.

Variant IDs обрабатываются в одинаковом порядке, чтобы уменьшить риск взаимных блокировок при заказах из нескольких SKU.

## 10. Почему cart_items.variant_id без ForeignKey

Это осознанное решение для совместимости с поведением `v0.4/v0.5`.

Сценарий:

```text
variant добавлен в cart
        ↓
variant удалён из catalog
        ↓
cart всё ещё содержит stale variant_id
```

`GET /cart` умеет очистить такую позицию, а checkout возвращает корректную business error.

Если сделать жёсткий FK с `RESTRICT`, удаление SKU перестанет работать как раньше.

Если сделать `CASCADE`, позиция исчезнет из корзины на уровне БД без участия domain/service logic.

Поэтому на текущем этапе сохранён soft reference.

## 13. Почему тесты используют SQLite

Полный unit/API regression suite не должен требовать поднятого Docker/PostgreSQL на каждой машине.

Поэтому:

```python
create_app()
```

создаёт отдельный:

```text
sqlite+pysqlite:///:memory:
```

При этом используются **те же SQLAlchemy repositories**, services и routers.

Отдельные v0.6 tests проверяют:

- Alembic schema;
- 20 seeded products;
- 25 variants;
- persistence между двумя app instances;
- DB-backed health;
- OpenAPI version.

Runtime объект:

```text
app.main:app
```

использует `PETSHOP_DATABASE_URL` и по умолчанию настроен на PostgreSQL.

## 20. Чистая установка v0.6.0 с нуля

> Инструкция относится к отдельному архиву **v0.6.0**.

Требования: Python 3.12+ и PostgreSQL. Для Windows рекомендуемый вариант — Docker Desktop + Docker Compose; отдельная установка PostgreSQL при этом не нужна.

### 1. Перейти в проект

```powershell
cd C:\Users\s.kirill\Desktop\petshop-api-v0.6.0
```

### 2. Создать `.venv` и установить зависимости

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### 3. Запустить PostgreSQL

```powershell
docker compose up -d postgres
docker compose ps
```

Ожидается `Up ... (healthy)`.

### 4. Применить миграции

```powershell
.venv\Scripts\python.exe -m alembic upgrade head
```

На чистой БД будет применена `0001_v060`, которая создаёт таблицы и seed-каталог.

### 5. Запустить API

```powershell
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --no-use-colors
```

Проверка:

```text
Swagger  http://127.0.0.1:8000/docs
Health   http://127.0.0.1:8000/health
```

`/health` должен вернуть `"storage": "postgresql"`.

## 21. Обновление v0.5.0 → v0.6.0

Это переход с in-memory на PostgreSQL. Автоматического переноса runtime-данных v0.5 нет.

1. Остановить v0.5.
2. Запустить PostgreSQL через `docker compose up -d postgres`.
3. Установить зависимости v0.6.
4. Выполнить `alembic upgrade head`.
5. Запустить v0.6.
6. Пользователей/корзины/заказы из памяти v0.5 создать заново; демонстрационный каталог создаётся migration.
