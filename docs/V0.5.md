# Petshop API v0.5.0 — Orders

## Зачем появилась версия v0.5.0

`v0.4.x` завершила работу с персональной корзиной, но корзина ещё не являлась фактом покупки. Цена в ней оставалась «живой», остаток мог измениться, а история покупок отсутствовала.

`v0.5.0` вводит отдельный домен **Orders** и завершает первый полноценный пользовательский сценарий магазина:

```text
регистрация → login → каталог → корзина → checkout → заказ
```

Это minor-версия, а не patch, потому что API получил новый самостоятельный функциональный модуль, новые доменные сущности и новые HTTP endpoints.

## Что добавлено

### Доменная модель

Добавлены две сущности без зависимости от FastAPI/Pydantic/SQL:

```text
Order
└── OrderItem
```

`OrderItem` — это snapshot одной купленной позиции. Он хранит:

- `product_id`;
- `product_name`;
- `variant_id`;
- `sku`;
- `variant_label`;
- `unit_price`;
- `quantity`;
- `currency`.

`Order` хранит:

- `id`;
- `user_id`;
- `status = created`;
- `created_at`;
- immutable tuple позиций;
- `total_items`;
- итоговую сумму `total`.

## Почему заказ хранит snapshot

Корзина специально использует текущие данные каталога. Заказ — наоборот, исторический документ.

Пример:

```text
До покупки:
DEMO-2-S = 1 400 ₸

Покупка:
OrderItem.unit_price = 1 400 ₸

Позже каталог изменили:
DEMO-2-S = 1 800 ₸

Старый заказ:
OrderItem.unit_price = 1 400 ₸
```

То же правило применяется к названию товара, SKU и названию варианта. Изменение каталога после checkout не переписывает историю заказа.

## Архитектура

Новый модуль повторяет архитектурное разделение проекта:

```text
HTTP Request
     ↓

     ↓

```

Файлы:


Так же, как Catalog/Users/Cart, Orders не привязан к будущему SQL-хранилищу.

## Checkout

Endpoint:

```http
POST /api/v1/orders
Authorization: Bearer <token>
```

Тело запроса не требуется. Источником является корзина текущего пользователя.

Алгоритм:

```text
1. Получить корзину пользователя
2. Проверить, что она не пуста
3. Найти каждый variant_id в каталоге
4. Повторно проверить остаток КАЖДОЙ позиции
5. Собрать OrderItem snapshots
6. Создать Order
7. Списать stock
8. Сохранить Order
9. Очистить Cart
10. Вернуть 201 Created
```

## Почему остаток проверяется повторно

Между добавлением позиции в корзину и checkout каталог может измениться.

Поэтому `can_checkout=true` в ответе корзины является текущей информацией, но финальное решение всегда принимает `OrderService.checkout()` непосредственно перед покупкой.

Если хотя бы одной позиции недостаточно:

```text
Order не создаётся
stock не меняется ни у одной позиции
Cart не очищается
HTTP 409
```

Это защищает от частично оформленного заказа.

## In-memory атомарность

В `v0.5` база данных ещё не используется. `OrderService` применяет process-local `RLock`, чтобы два checkout внутри одного экземпляра приложения не списали один и тот же остаток одновременно.

Кроме того, checkout разделён на две фазы:

```text
PHASE 1 — validate everything
PHASE 2 — mutate state
```

Сначала проверяется вся корзина. Только после успешной общей проверки начинается изменение остатков.

При неожиданной ошибке во второй фазе сервис восстанавливает:

- предыдущие остатки;
- заказ в repository;
- содержимое корзины.

В `v0.6` эту ответственность заменит транзакция PostgreSQL/SQLAlchemy.

## Очистка корзины

Корзина очищается только после успешного сохранения заказа.

Это принципиально отличается от подхода:

```text
clear cart → попробовать создать order
```

который мог бы потерять пользовательскую корзину при ошибке.

## API

### Создать заказ

```http
POST /api/v1/orders
```

Успех:

```http
201 Created
```

Пример ответа:

```json
{
  "id": 1,
  "user_id": 1,
  "status": "created",
  "created_at": "2026-09-21T06:00:00Z",
  "items": [
    {
      "product_id": 2,
      "product_name": "Корм для собак №2",
      "variant_id": 20,
      "sku": "DEMO-2-S",
      "variant_label": "400 г",
      "unit_price": "1400.00",
      "currency": "KZT",
      "quantity": 2,
      "line_total": "2800.00"
    }
  ],
  "total_items": 2,
  "total": "2800.00",
  "currency": "KZT"
}
```

### История заказов

```http
GET /api/v1/orders
```

Возвращаются только заказы текущего JWT-пользователя, новые первыми.

### Один заказ

```http
GET /api/v1/orders/{order_id}
```

Пользователь может читать только свой заказ.

Если ID принадлежит другому пользователю, API отвечает тем же `404`, что и для отсутствующего ID. Это не раскрывает существование чужого заказа.

## Коды ошибок

### POST /api/v1/orders

- `201` — заказ создан;
- `401` — нет корректного Bearer JWT;
- `409` — корзина пуста, variant исчез или остатка недостаточно;
- `422` — нарушены инварианты данных заказа.

### GET /api/v1/orders/{order_id}

- `200` — заказ найден;
- `401` — нет корректного Bearer JWT;
- `404` — заказ не существует у текущего пользователя;
- `422` — некорректный path parameter.

## Что не добавлялось

`v0.5` сознательно остаётся без SQL.

Также пока нет:

- оплаты;
- доставки;
- адресов;
- статусов `paid/shipped/delivered/cancelled`;
- отмены заказа;
- возврата остатков;
- ролей администратора;
- резервирования товара при помещении в корзину.

На этом этапе единственный бизнес-статус заказа — `created`.

## Тестирование

После перехода `v0.4.1 → v0.5.0` весь регрессионный набор сохранён и расширен.

Проверяются:

- ООП-модель `Order`/`OrderItem`;

- защита чужого заказа;

- изоляция in-memory application instances;
- Swagger/OpenAPI `v0.5.0`.

Результат полного прогона:

```text

```

Дополнительно выполнен live HTTP QA через реально запущенный Uvicorn: `10/10` проверок прошли, включая `/openapi.json`, JWT, cart, checkout, историю заказов и фактическое уменьшение stock.

## Изменение версии

```text
v0.4.1
Cart + Swagger QA
      ↓
v0.5.0
Orders + Checkout + Stock mutation + Order history
```

`v0.5.0` — новая функциональная стадия. Поэтому увеличена minor-часть (`0.4 → 0.5`), а patch сброшен в `0`.

## Следующий этап

```text
v0.6 — PostgreSQL + SQLAlchemy
```

На `v0.6` интерфейсы Repository сохраняются, а in-memory реализации начинают заменяться SQL-реализациями. Основная бизнес-логика Router/Service должна остаться максимально стабильной.

## Обновление v0.4.1 → v0.5.0

1. Использовать исходники v0.5.0.
2. Установить зависимости текущей версии.
3. Перезапустить API.
4. Учесть, что состояние предыдущей in-memory версии не переносится.
5. Проверить checkout и историю заказов.
