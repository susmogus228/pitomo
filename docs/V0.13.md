# Питомо 0.13.0: доставка

Покупатель видит три этапа доставки: «На складе» (`warehouse`), «В пути»
(`in_transit`), «Рядом с вами» (`nearby`). Администратор меняет этап в карточке
заказа в `/admin/orders`. Доставка остаётся тестовой: служба доставки, GPS курьера
и расчёт времени прибытия не подключены.

## Этапы и поломки

Администратор переводит заказ только на следующий этап. На любом этапе он может
отметить прокол шины (`flat_tire`), переворот грузовика (`overturned`) или проблему
с двигателем (`engine_failure`), добавить
пояснение и затем устранить проблему. При активной поломке переход запрещён.
Грузовик и дорога останавливаются; после устранения проблемы движение продолжается.
Покупатель может остановить анимацию. Сайт учитывает системное ограничение движения.
При проблеме с двигателем у фургона открыт капот, кот чинит двигатель снаружи,
над мотором поднимается дым.
После устранения проблемы капот закрывается, дым исчезает и движение продолжается.

Неоплаченный заказ с тестовой оплатой нельзя отправить. Заказ с оплатой при
получении можно отправить, но сайт не отмечает его оплаченным автоматически.
После отправки покупатель не может отменить заказ с возвратом товара на склад.
После отмены или подтверждения получения администратор не меняет доставку.
Для самовывоза этапов доставки нет.

Покупатель подтверждает получение доставки на этапе «Рядом с вами», когда нет
активной поломки. Затем он может оставить отзыв. Сам переход на последний этап
не подтверждает получение. Для самовывоза сохраняется прежнее подтверждение.

Страница заказа обновляет данные в фоне. При ошибке соединения покупатель видит
последний полученный статус и сообщение о сбое обновления. Сбой соединения не
меняет этап и не означает поломку грузовика.

## API

Ответы заказов содержат `delivery_tracking`. Для самовывоза это `null`, для
доставки объект со свойствами:

| Поле | Значение |
| --- | --- |
| `stage` | `warehouse`, `in_transit`, `nearby` |
| `incident` | `null`, `flat_tire`, `overturned`, `engine_failure` |
| `incident_note` | Пояснение администратора или `null` |
| `updated_at` | Время последнего изменения или `null` для старого заказа без событий |
| `version` | Версия состояния для защиты от одновременных изменений |
| `history` | События с `event_type`, `stage`, `incident`, `note`, `occurred_at` |

Типы событий: `created`, `stage_changed`, `incident_reported`, `incident_resolved`.

`PATCH /api/v1/admin/orders/{id}/delivery` требует входа администратором и
существующую защиту браузерных запросов. Отправляйте `expected_version` из
последнего ответа и одну команду:

```json
{"expected_version": 0, "stage": "in_transit"}
```

```json
{"expected_version": 1, "incident": "flat_tire", "incident_note": "Меняем колесо"}
```

```json
{"expected_version": 2, "incident": null}
```

Сервер возвращает полный заказ администратора. Устаревшая версия или запрещённый
переход возвращают `409`; неверный формат команды возвращает `422`. После `409`
загрузите актуальный заказ и выберите действие заново. Повтор команды с актуальной
версией, не меняющей состояние, не добавляет событие и не увеличивает версию.

## Обновление базы

Перед запуском миграции сохраните базу и том загруженных фотографий согласно
[инструкции эксплуатации](OPERATIONS.md). Миграция `0011_v013` следует за
`0010_v012` и сохраняет пользователей, товары, заказы и остатки. Существующие
доставки начинают с этапа «На складе»; уже полученные доставки получают этап
«Рядом с вами». Миграция не создаёт вымышленную историю прошлых перемещений.
После обновления `/ready` должен возвращать ревизию `0011_v013`.

## Исправление каталога

При проверке обновления исправлено двойное добавление варианта товара в
SQLAlchemy relationship. Ответ сразу после создания товара теперь содержит
каждый SKU один раз. Исправление не изменяет существующие записи базы.
